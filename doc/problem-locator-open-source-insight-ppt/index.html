OPEN-SOURCE AI-SRE INVESTIGATION FRAMEWORK

OpenSRE：开源的线上故障调查 Agent 框架

核心定位

OpenSRE 自己实现了一套线上故障调查 Agent 运行机制：通用大模型负责推理、提出假设和选择下一步；外层流水线负责解析告警、确定工具范围，并在调查结束后调用推理模型提取 RCA 字段，再由外层交付结果；OpenSRE 运行时负责向模型提供提示词和范围内的工具定义、执行工具调用、控制循环、记录证据和管理上下文。

端到端用途
接收告警 查询运维数据 验证根因假设 输出调查报告
核心组成 固定调查流水线 单个故障调查 Agent 运维工具集成 评测机制
01
接入现有系统

通过工具接入企业已有的日志、指标、调用链、发布、数据库和云平台，无需迁移全部数据。

日志指标调用链发布 / 云平台
02
Agent 动态调查

不依赖 RPC 超时等固定故障剧本；Agent 在允许的工具范围内提出假设、选择查询并迭代验证。

单 Agent动态选工具逐轮验证
03
结论附带证据

报告给出可能根因、原因链、查询结果、未确认项与处置建议，供人工核对。

查询结果原因链未确认项

第 3 步代码确定本次调查的工具边界 第 4 步故障调查 Agent 在边界内动态查询，具体循环见下一页
03
代码确定工具边界确定性选择，不调用模型规划
  • 候选来自已注册且当前可用的调查工具，再按固定规则排序。
  • planned_actions 是工具名短名单；阶段还记录选择理由、审计信息及建议检索参数。
  • 它不提出根因假设，也不生成每次实际工具调用的查询语句。默认预算 10 个，可配 1—50 个；入选数可少于预算。
  • 正常情况下 Agent 只获得短名单中仍可用的工具；计划为空或全部失效时，才进入最多 32 个工具的回退筛选。
04
Agent 在边界内动态调查模型决策 + OpenSRE 运行时执行
  • 对于已配置种子查询的告警来源，OpenSRE 运行时代码会在首次调用模型前执行该查询。
  • 模型读取告警和已有证据，决定下一工具、查询参数、时间范围和是否继续。
  • Agent 结束后，外层第 5 步 diagnose 通常调用推理模型，以结构化输出从最终文本提取 RCA 字段；失败时回退旧解析器。它不继续调查，也不做独立复核。
  • 随后，外层第 6 步 deliver 生成、保存或发送报告。
外层实现：六步由 Python 按固定顺序编排：第 3 步按规则选工具，第 4 步运行调查模型循环，第 5 步通常调用推理模型，以结构化输出提取字段；失败时回退旧解析器。 当前缺口：retrieval_controls 中的建议时窗与结果数量，尚未被 Agent / 工具执行链强制注入真实调用参数。

03 / 04 · Agent 实现逻辑
CONNECTEDINVESTIGATIONAGENT.RUN

OpenSRE 自己实现的故障调查 Agent 怎样运行

ConnectedInvestigationAgent= 调查提示词可用工具模型调用循环工具执行证据记录运行控制
提示词引导 分诊提出假设查询验证处置建议 不是代码状态机；首轮新工具结果返回后，运行时会追加一次 checkpoint，推动模型明确
分诊结论、根因假设与待确认问题
01
准备本次运行

读取当前流水线中的告警、解析字段、连接信息和工具短名单；新建消息历史、证据集合和工具调用缓存。

02
可选的预设种子查询

如告警来源已配置种子查询，OpenSRE 运行时会在首次调用模型前执行；结果写入证据并加入模型上下文。

单 Agent 调查循环查询结果返回同一个模型继续推理
03模型决定下一步

提出假设，选择工具，生成查询参数和时间范围。

04运行时检查并执行

校验模型可填写的调用参数；受保护连接字段由运行时注入。同轮默认并行，遇到串行工具则整批顺序执行；异常以错误结果送回循环。

05记录新证据

新结果加入模型消息，并写入脱敏的 EvidenceEntry；缓存复用不新增证据条目。

06继续或结束

有新调用则进入下一轮；无工具调用时检查结论标记，首次缺失最多再提示一次。模型调用上限为 20 次。

继续：证据回到步骤 03，模型调整假设与查询 结束：最后一条助手消息 + 证据 + 循环次数 → 外层流程
A模型上下文长度控制

每轮调用模型前，运行时估算系统提示词、工具定义和消息历史的总长度。本轮输入上限 = 模型上下文窗口 − 为输出预留 16,000 个 token。

  1. 超限时优先删除完全重复的工具调用及其返回结果，同类中先删除占用最大的。
  2. 再删除占用最大的非种子工具调用及其返回结果；种子查询的调用及返回结果不整组删除。
  3. 仍超限才截断最大可裁剪消息。
这是消息历史的删除与截断，不是自动总结；被裁内容不再进入后续模型调用，但脱敏的 EvidenceEntry 仍单独保留。
B当前调查内复用相同工具调用

OpenSRE 运行时把工具名 + 模型或种子查询提供的输入参数按键排序规范化，作为缓存键；受保护连接字段不计入缓存键。完全相同且仍在缓存中的调用直接复用结果；参数变化时重新执行。缓存按最近最少使用（LRU）策略淘汰条目。

最多 128 项缓存条目约 200 万字符缓存总容量8,000 字符重复结果回放上限
如果连续两轮的全部工具调用都命中缓存，下一轮将不再向模型提供工具，只要求它输出结论。
实现边界 上下文裁剪与缓存由 OpenSRE 运行时负责，不是模型能力 同轮工具并行 ≠ 多 Agent 协作 diagnose 通常调用推理模型提取字段；不继续调查或独立复核 计划阶段的建议检索参数未被强制采用

4B
模型首轮分诊：选择调用链查询

4C
模型提出假设，并选择日志验证

模型提出“库存服务在等待数据库连接”的假设并选择日志查询；运行时执行后发现，日志从 10:00 起出现 connection acquisition timeout after 3000ms。

4D
模型继续选择发布与配置查询

OpenSRE 运行时执行后发现：09:58 发布的 inventory-service v4.8.3 将连接池上限从 80 改成 8。

4E
模型选择指标查询，继续交叉验证

模型生成查询参数，运行时执行并返回：活动连接数 active=8、等待请求数 waiters=120；数据库 SQL 耗时、CPU、网络和其他下游无对应异常。结果支持连接池耗尽判断，并降低其他原因的可能性。

Agent 结论 09:58 的发布将连接池上限由 80 改为 8；连接池耗尽使请求排队、库存服务响应超过 3 秒，触发上游 RPC 超时。
