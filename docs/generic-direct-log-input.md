# 通用定位直接读取用户日志

新建通用诊断直接读取用户上传的文本日志，不再依赖 Logparse 识别产品日志。专用诊断继续按 Skill 声明调用 Logparse，并保留时间、进程、槽位等前置输入要求。

## 文件准备与分析

- 单独的 `.log`、`.txt`、`.json`、`.jsonl`、`.ndjson` 文件按 UTF-8 文本读取，允许 UTF-8 BOM。JSON 类文件作为日志文本，不要求符合某个业务 schema。
- `.zip`、`.tar`、`.tar.gz`、`.tgz`、`.gz` 由框架安全展开，保留原始文件内容，不要求固定的产品目录或 `.log` 后缀。嵌套归档不递归展开。
- 每个文件独立校验；不同附件中的同名文件保留各自来源，同一归档内重复或冲突的成员路径会被拒绝。仍最多选择 20 个附件，单文件上传上限 2.5 GiB，总上传量上限 5 GiB。
- 单次准备的展开总量和可读文本总量分别限制为 1 GiB，最多处理 10,000 个文件或目录，路径最多 32 层，清单最多 2,000,000 字节。归档另有压缩比和元数据限制。准备过程还受执行时限与磁盘容量约束；上传成功不代表展开后的内容一定在限额内。
- `inputs/generic_logs.json` 的 v3 清单记录 `preparation: "direct-v1"`、`sources`、可读 `logs`、未采用的 `skipped` 和 `coverage`。每条可读日志保留原附件 ID、名称、SHA-256、成员相对路径、文件大小和 SHA-256，并提供只读 `log_path`。
- Skill 按需检索和分段读取，日志正文不整体写入提示词。报告要说明实际使用的附件、路径、行号和关键摘录；清单存在不代表模型已读完全部日志。

空文件、二进制、无法按 UTF-8 读取的文件和嵌套归档会记录原因。部分可读时继续分析可读文件；没有可读日志时说明原因，再按原始问题和补充文字继续定位，由 Skill 判断 `RESOLVED` 或 `UNRESOLVED`，不得把文字分析当作日志验证。

损坏归档、路径穿越、链接等不安全成员和超限输入明确失败，不静默跳过安全检查。框架不自动猜测字符编码、不调用 Logparse 兜底；专有二进制格式应先由用户导出可读文本，或使用适用的专用定位。

## 会话与旧数据

创建 Case 时仍先导入所选附件，再启动分析。运行中换日志继续使用同 Case、同轮次的取消与重启流程；新消息中的附件列表是新的完整选择。重复请求不重复执行，停止或删除后不会启动待重启任务。

报告后的追问仍读取原报告对应的只读日志快照；新附件只作为待核对材料登记，需要使用时由框架交接到新的正式诊断轮次。来源、跳过原因和处理范围随快照保留。纯文字报告不会仅因存在附件就宣称追问可读取日志。

追问快照继续使用原有独立容量限制，单份默认上限为 1 GiB，其中还包含报告和清单。接近通用日志准备上限的输入可能无法完整保存为追问快照；此时按现有规则降为仅基于报告回答，并说明日志不可用，不影响已经生成的诊断报告。

新 Job 固定 `generic_log_preparation="direct-v1"`。旧 Job 未包含该字段时保留原 Logparse 计划、产物和空清单直接 `UNRESOLVED` 的行为，不因升级重新解释其输入。`GENERIC_LOGPARSE_PRODUCT` 只保留旧任务兼容用途；本次不调整专用 Skill 的注册要求。

保留旧准备策略不代表升级后能自动恢复执行中的任务。旧 Job 固定的 `(id, version, hash)` 运行资产仍须可用；缺失时按原有 `ASSET_VERSION_UNAVAILABLE` 处理，不自动替换成新 profile 或新准备策略。服务退出及任务中断继续遵守现有恢复规则。

仅使用通用定位且没有依赖 Logparse 的专用 Skill 时，部署可同时省略 `LOGPARSE_REPO` 和 `LOGPARSE_CONFIG_PATH`。两项必须成对提供或省略；只要配置了 Logparse，就继续严格校验。存在依赖 Logparse 的专用 Skill 时仍必须配置，缺失会拒绝启动。执行旧 Generic Job 仍需要其原 Logparse 运行环境，不能用新直读流程替代历史绑定。

原始附件、展开副本和追问快照沿用现有资源归属、容量预约、取消与清理机制。Web 日志默认保留 15 天，磁盘紧张时可能提前清理已完成轮次；会话正文、报告和已有问答长期保留。详见[文件保留与清理](storage-retention.md)。

## 网站适配

消息仍使用 `text`、`attachment_ids`，不新增日志模式参数，也不增加公开 MCP 工具。文件选择器加入文本后缀，预约与 PUT 保持相同 MIME：

| 文件后缀 | `content_type` |
| --- | --- |
| `.log`、`.txt` | `text/plain` |
| `.json` | `application/json` |
| `.jsonl`、`.ndjson` | `application/x-ndjson` |
| `.jsonl` 的显式调用 | 也接受 `application/jsonl` |
| `.zip` | `application/zip` |
| `.tar` | `application/x-tar` |
| `.tar.gz`、`.tgz`、`.gz` | `application/gzip` |

沿用小写后缀检查。上传成功只表示附件 `READY`，不代表已被本轮采用，也不保证其中所有内容可分析。专用流程只采用符合其 Skill 日志要求的附件；不能因上传入口支持文本，就去掉专用流程的归档约束。

进度新增 `GENERIC_LOG_PREPARE`，文案为“正在准备日志”。优先展示服务端 `progress.message`；保留旧 `LOGPARSE` 展示，用于专用诊断和旧 Generic Job。文件没有可读内容时，直接展示报告中的限制与文字分析，不在前端改写报告结论。

## 验证范围

专项应覆盖：原始文本实际字节读取、UTF-8 BOM、多包同名文件、大文件分段读取、部分及全部不可读、损坏或不安全归档、预算与取消、换包重启、报告追问快照和资源清理，以及旧 Job 与专用流程兼容。真实 Linux Skill 验收还需确认其读取日志并引用真实线索；协议握手或确定性模拟不等于真实模型分析验收。
